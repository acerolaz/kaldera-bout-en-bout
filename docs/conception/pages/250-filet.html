2.5🛟 Si le système plante : exécution durable

Quand l'équipe ne peut plus conclure, un mécanisme hors équipe reconstruit une escalade humaine depuis l'état partagé. C'est le pattern exécution durable (checkpointing) ; son niveau 2 demande une base PostgreSQL (snapshots et verrou).

Niveau 2 · le processus meurt si une base est configurée
☠️ Le processus s'arrête netmémoire saturée, arrêt forcé, redémarrage
↓
💾 Snapshot après chaque transitionPostgreSQL · demandes.etat jsonb · clé = reference · statut = en_cours
↓
⏱️ Reaper indépendant (make reaper, toutes les 10 s)inactive depuis KALDERA_REAPER_AGE_S (30 s) ⇒ en_cours → secours (atomique)
↓
📋 Fiche reconstruite depuis le snapshotmême format · trace jusqu'au dernier état + étape « reaper »
🧑‍💼 File humaine : gestionnaire ou cellule_fraude — le dossier est REPRIS par un humain, jamais rejoué
-- verrou compare-and-set atomique : deux reapers ne peuvent pas escalader deux fois
UPDATE demandes SET statut = 'secours', maj = now()
WHERE (statut = 'en_cours' OR (statut = 'secours' AND fiche IS NULL))
  AND maj < now() - make_interval(secs => 30)
RETURNING reference, etat;   -- 0 ligne ⇒ un autre reaper (ou la fin normale) a gagné
-- secours sans fiche : un classement raté est repris au passage suivant
🔒 Le verrou « en_cours → secours » empêche une double escalade si le traitement finit malgré tout : la fin normale (terminer) ne s'applique qu'à une demande encore en_cours. Une seule requête SQL, atomique (2.6).

Pourquoi hors équipe ?

⚖️ decision peut être celui qui a planté : le filet ne dépend d'aucun agent. Tracé filet_securite. La base ne bloque jamais une décision : au premier échec d'écriture, la persistance est coupée pour la demande.
