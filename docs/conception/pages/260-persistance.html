2.6🐘 Persistance PostgreSQL

Une seule base pour les fichiers, les contrats, les snapshots, le registre A2A et l'espace assuré — dès que KALDERA_DATABASE_URL est configurée. Sans elle, le moteur tourne en mémoire (traiter_demande, make scenarios). Trois garanties de conception sont portées par des contraintes SQL.

-- ① 1 appel partenaire par dossier (contrat §6) : la réservation PRÉCÈDE l'envoi
INSERT INTO appels_partenaire (reference) VALUES (%s)
ON CONFLICT (reference) DO NOTHING RETURNING reference;        -- 0 ligne ⇒ pas d'envoi
-- ② reaper : compare-and-set atomique, pas de double escalade
UPDATE demandes SET statut = 'secours', maj = now()
WHERE (statut = 'en_cours' OR (statut = 'secours' AND fiche IS NULL)) AND maj < now() - make_interval(secs => %s)
RETURNING reference, etat;
-- ③ worker d'ingestion : plusieurs workers, aucune tâche prise deux fois
SELECT id, sha256, tache, reference FROM file_ingestion WHERE statut = 'en_attente'
ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1;

🧪 Tests

Unitaires sans base (rapides, bloquants) ; intégration make test-integration sur un PostgreSQL en conteneur (docker compose --profile integration, port 5433), base vidée à chaque test.

🧭 .NET

bytea ≈ varbinary(max) ; SKIP LOCKED ≈ READPAST ; adaptateurs ≈ repositories Dapper / EF Core ; pool ≈ NpgsqlDataSource.

Une seule base, facultative

Fichiers, contrats, snapshots, cache d'analyse, registre A2A et comptes assurés : PostgreSQL dès qu'il est configuré (EX-D41). Base configurée mais en panne : aucun envoi au partenaire, et la décision n'attend jamais la base.

Claim check préservé

demandes.etat ne contient que des piece_id, jamais d'octets ; table blobs séparée = déduplication par sha256.

Trois garanties en SQL

1 appel partenaire, pas de double escalade, pas de tâche prise deux fois : chacune tient en une requête, et survit à un redémarrage.
