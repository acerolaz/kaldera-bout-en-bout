3.4🚦 Codes d'erreur JSON-RPC ↔ HTTP

Le partenaire répond en JSON-RPC : la plupart des erreurs arrivent dans le corps (error.code). L'équivalent HTTP aide à lire comme en REST. Toutes donnent un avis indisponible, avec une cause courte et une nature d'appel pour les métriques.

ERR · Réponse d'erreur (détail illustratif dans error.data) 
{
  "jsonrpc": "2.0",
  "id": "c0a8012e-4f1b-4c55-9d1e-2b7e1f0e6a10",
  "error": {
    "code": -32602,                         ◀ ⑧
    "message": "Invalid params",
    "data": {                               ◀ ⑨
      "champ": "code_postal",
      "raison": "champ non autorisé"
    }
  }
}
  • ⑧ -32602 ≈ 422 : notre requête est fautive ; la projection doit être corrigée. Cause : « JSON-RPC -32602 : projection refusée ».
  • ⑨ error.data et message ne sont jamais lus : la cause ne retient que le code, et un code non entier devient « ? » (EX-D22).
⚠️ Piège : en JSON-RPC, une erreur métier arrive souvent avec un HTTP 200. Le client lit toujours error.code dans le corps avant le statut : tester seulement le statut HTTP laisserait passer une erreur pour un succès.
🔁 Quelle que soit l'erreur : statut indisponible ⇒ mode dégradé §9 (3.5), et aucune relance.
